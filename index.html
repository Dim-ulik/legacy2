Миграция изменений QGroundControl на Stable_V5.1

Исходные данные

Мы переносим пользовательские изменения старой версии QGroundControl в Stable_V5.1. Работайте с тремя отдельными деревьями: пользовательское показывает нужное поведение, оригинальное помогает отделить правки, целевое служит основой результата.

КопияДля чего нужнаЧто с ней делать
Модифицированный проектИсточник функции подготовки, настроек, переводов и сборочных дополненийЧитать и брать отдельные компоненты для адаптации
Оригинальный QGroundControlПонять, что именно было добавлено пользователемИспользовать для сравнения
Stable_V5.1Новая архитектура, в которую переносится функциональностьВносить изменения в отдельной рабочей ветке

Репозиторий: github.com/mavlink/qgroundcontrol.

Как пользоваться этой инструкцией

  • В каждом пункте сначала прочитайте объяснение, затем найдите указанный файл и место интеграции.
  • Блоки кода ниже — примеры и отдельные фрагменты. Комментарии указывают, куда их вставлять; ими не нужно заменять существующие файлы целиком.
  • Сохраните новые обработчики и функции целевой версии. Переносимый старый код может не знать о них.
  • Сначала проверьте сборку неизменённой цели. Затем меняйте небольшие связанные части и выполняйте проверки после каждой.

Практический порядок работы

Удобнее начать с настроек (§1.3), затем адаптировать данные (§1.4), правила и сессию (§1.5–1.6), после этого подключать QML (§1.1–1.2). Далее — видимость, меню, проверка GPS, переводы и упаковка. Порядок разделов исходного документа сохранён в оглавлении.

Цель: сохранить пользовательские возможности и одновременно оставить в работе новые функции целевой версии.

1. Новая функция Flight Preparation

Flight Preparation — окно подготовки к полёту. Оно собирает телеметрию и результаты проверок, позволяет отметить ручные проверки и сделать текстовый отчёт. Это дополнительный инструмент: штатные разрешения на arm/takeoff остаются у QGroundControl и автопилота.

  3. Приложение собирается в release-режиме, а не только запускает случайно найденные локальные файлы.

1.1. Адаптация QML

Этот этап означает: переносимые экраны подготовки нужно приспособить к Qt 6 и структуре новой версии QGC. Изменения ниже относятся к файлам FlightPreparation*.qml, которые добавляются в src/FlyView/.

Примеры показывают конкретные замены. Они не заменяют содержимое файлов целиком: интерфейс и логику подготовки нужно сохранить.

Импорты определяют, какие элементы доступны в QML. «Versionless imports» означает, что после названия модуля больше не указываются номера версий.

Если файл использует FactTextField или FactCheckBox, добавьте:

Для элементов, работающих с Facts

Названия QGCPalette и ScreenTools в самом коде остаются прежними — меняется способ их подключения. Подключайте только модули, которые использует конкретный файл.

3. Исправить проверку видимости настроек

У группы настроек в целевой версии свойство называется userVisible. Например, в FlightPreparationShowAction.qml условие показа действия выглядит так:

FlightPreparationShowAction.qml · свойство visible действия
visible:
    QGroundControl.settingsManager.flightPreparationSettings.userVisible
    && QGroundControl.settingsManager.flightPreparationSettings
         .showPreparation.rawValue

Здесь должны выполняться два условия:

  • userVisible — разрешено ли показывать эту группу настроек;
  • showPreparation.rawValue — включил ли пользователь инструмент подготовки.

Не заменяйте все visible в файлах. Свойство visible у кнопок, панелей и других визуальных элементов остаётся. Меняются обращения именно к настройкам: например, settings.visible становится settings.userVisible.

Не добавляйте условие наличия _activeVehicle для открытия подготовки: пользователь должен иметь возможность открыть окно без подключённого аппарата. Проверки, которым нужна живая телеметрия, при этом остаются недоступными или показывают неизвестный результат согласно правилам.

4. Открывать диалоги через фабрику

QGCPopupDialogFactory создаёт окно с правильным родителем и позволяет штатному механизму QGC управлять его жизненным циклом. Для ResetDialog внутри popup примените такую же схему: factory + Component + factory.open().

  1. Нажатие Preparation действительно открывает окно.
  2. Окно доступно и без подключённого аппарата.
  3. Заметка и отметки сохраняются при закрытии и повторном открытии.
  4. Уход из Fly View не оставляет окно со ссылкой на уничтоженную модель.

2. Зарегистрировать класс для Qt 6

Форма FlightPreparationSettings.h — добавьте все девять Facts
#pragma once
#include <QtQmlIntegration/QtQmlIntegration>
#include "SettingsGroup.h"

class FlightPreparationSettings : public SettingsGroup {
    Q_OBJECT
    QML_ELEMENT
    QML_UNCREATABLE("")
public:
    explicit FlightPreparationSettings(QObject* parent = nullptr);
    DEFINE_SETTING_NAME_GROUP()
    DEFINE_SETTINGFACT(showPreparation)
    DEFINE_SETTINGFACT(minimumBatteryPercent)
    // Остальные семь DEFINE_SETTINGFACT — по таблице выше.
};

QML_ELEMENT регистрирует тип. QML_UNCREATABLE означает: QML может обращаться к существующему объекту, но не должен создавать ещё одну группу. Сам объект создаст SettingsManager.

Форма FlightPreparationSettings.cc — дополните все Facts
#include "FlightPreparationSettings.h"

DECLARE_SETTINGGROUP(FlightPreparation, "FlightPreparation")
{
}
DECLARE_SETTINGSFACT(FlightPreparationSettings, showPreparation)
DECLARE_SETTINGSFACT(FlightPreparationSettings, minimumBatteryPercent)
// Остальные семь DECLARE_SETTINGSFACT — по той же схеме.

Старый вызов qmlRegisterUncreatableType из конструктора удалите: регистрация теперь декларативная. В Settings CMake добавьте .h/.cc в существующий список sources. JSON должен попасть в ресурс :/json/FlightPreparation.SettingsGroup.json через целевой helper.

3. Дать QML доступ к группе через SettingsManager

В SettingsManager.h добавьте следующие части в соответствующие разделы класса; это не отдельный новый класс manager:

Фрагменты SettingsManager.h
// Перед классом — предварительное объявление типа:
class FlightPreparationSettings;

// В классе рядом с другими настройками:
Q_MOC_INCLUDE("FlightPreparationSettings.h")
Q_PROPERTY(QObject* flightPreparationSettings
           READ flightPreparationSettings CONSTANT)

// public:
FlightPreparationSettings* flightPreparationSettings() const;

// private:
FlightPreparationSettings* _flightPreparationSettings = nullptr;

Предварительное объявление позволяет использовать указатель без полного include в header. Q_MOC_INCLUDE даёт Qt-генератору сведения о типе. Q_PROPERTY делает объект доступным для QML; getter возвращает существующий экземпляр.

Фрагменты SettingsManager.cc
#include "FlightPreparationSettings.h"

// В существующем SettingsManager::init(), после загрузки settings:
// _flightPreparationSettings = new FlightPreparationSettings(this);

FlightPreparationSettings*
SettingsManager::flightPreparationSettings() const
{
    return _flightPreparationSettings;
}

Используйте init() целевой версии, а не старый setToolbox. Родитель this задаёт время жизни группы вместе с SettingsManager.

1.4. Адаптация Snapshot к API целевой версии

Snapshot — обычный JS-объект с текущими данными. Он собирает сведения из Vehicle, параметров, GPS, батарей и миссии. Rules затем оценивает этот объект, не обращаясь ко всем компонентам напрямую.

«Сохранить контракт» означает оставить прежние имена полей результата. Например, поле снимка по-прежнему называется missionDistance, хотя исходное свойство контроллера теперь называется иначе.

Старое чтениеНовое чтениеПочему
vehicle.autopilot.setupCompletevehicle.autopilotPlugin.setupCompleteИзменилось имя свойства Vehicle
vehicle.rcRSSI как числоfactValue(vehicle.rcRSSI)Теперь rcRSSI — объект Fact, из него нужно получить rawValue
mission.missionDistancemission.missionTotalDistanceПереименовано свойство общего расстояния
mission.missionItemCountДобавить read-only свойство в MissionControllerСтарого публичного счётчика больше нет

1. Обновить чтение полей в FlightPreparationSnapshot.js

Фрагмент объекта, возвращаемого capture()
setupComplete: !!(vehicle && vehicle.autopilotPlugin
    && vehicle.autopilotPlugin.setupComplete),
rcRssi: vehicle ? factValue(vehicle.rcRSSI) : NaN,
missionDistance: mission ? mission.missionTotalDistance : NaN,
missionItems: mission ? mission.missionItemCount : 0

Проверки vehicle ? ... защищают от обращения к отсутствующему аппарату. NaN означает «число неизвестно»: это лучше, чем выдать нулевой заряд или нулевую потерю там, где данных вообще нет.

2. Восстановить точный счётчик команд миссии

Работайте в src/MissionManager/MissionController.h/.cc. Read-only означает, что интерфейс может читать количество, но не назначать его. NOTIFY — сигнал, по которому QML обновляет отображение.

// В public:

// В signals:

// В private:

В _newMissionItemsAvailableFromVehicle, сразу после получения newMissionItems и до обработки fake Home/visual items:

const int count = newMissionItems.count();
if (_missionItemCount != count) {

В _managerVehicleChanged сбрасывайте значение в 0 до ветки раннего выхода для nullptr. При изменении значения отправляйте тот же сигнал. Проверьте также удаление и загрузку пустой миссии.

Почему нельзя visualItems.count − 1: визуальный элемент может объединять несколько MAVLink-команд. Кроме того, список может содержать служебную Home-точку. Нужен размер исходного списка до этих преобразований, включая fake Home, если он передан прошивкой.

3. Сохранить правильные источники и обновления

  • Берите контроллер миссии Fly View из globals.planMasterControllerFlyView / _missionController. Контроллер Plan View может показывать редактируемую миссию, не соответствующую активному борту.
  • Перебирайте всю модель batteries, а не только батарею с индексом 0. Низкий заряд второй батареи тоже важен.
  • Учитывайте telemetryAvailable. Числовое значение, не полученное с борта, должно оставаться неизвестным.
  • Координаты проверяйте через QGeoCoordinate.isValid. Проверка if (latitude) ошибочно отвергнет широту 0°.
  • После изменения данных UI должен обновляться по уведомлениям. При необходимости добавьте Connections к фактическим сигналам объекта. Polling — периодический опрос таймером — здесь не нужен.

Как проверить результат

  1. Появление и изменение второй батареи обновляет результат без переоткрытия окна.
  2. Count совпадает с размером сырого списка при обычной миссии и миссии с объединяемыми элементами.
  3. Переключение аппарата на время загрузки не показывает счётчик предыдущего аппарата.
  4. Пустая миссия даёт 0; координаты (0,0) проходят проверку валидности.

1.5. Правила оценки

FlightPreparationRules.js отвечает на вопрос: что означают полученные данные для подготовки? Переносите исходный алгоритм, сохраняя порядок проверок: более ранняя ветвь может иметь приоритет над следующими.

СтатусПонятный смысл
okДля конкретной проверки получены подходящие данные
warningЕсть отклонение или сообщённая проблема, требующая внимания
unknownНедостаточно данных, чтобы сделать вывод
infoИнформационный результат: например, проверка не обязательна

1. Сначала проверить, можно ли доверять текущей связи

Условие доступности данных
live = connected && !linkLost && linkMonitoring
  • connected: выбран подключённый аппарат.
  • !linkLost: связь не признана потерянной.
  • linkMonitoring: механизм обнаружения потери связи включён.

Все три условия должны выполняться. Если связь потеряна, прежний хороший заряд остаётся в памяти, но не подтверждает текущую готовность. Сам результат Connection при потере связи — warning, а зависимые от live результаты становятся unknown по исходным правилам.

2. Сохранить каждую ветвь оценки

ПроверкаКак принимать решение
ConnectionНет аппарата → unknown. Потеря связи → warning. Мониторинг выключен или loss неизвестен → unknown. Loss выше maximum → warning.
ParametersMissing parameters → warning. Незавершённая первоначальная загрузка → unknown. Pending writes после готовности → warning. Иначе OK. Сохраните исходный приоритет ветвей.
SetupНужны live и готовые параметры. Незавершённая настройка аппарата → warning; без необходимых данных → unknown.
BatteryОтдельная строка для каждой батареи. Нет её телеметрии → unknown. ChargeState 2–6 → warning раньше проверки процента. Неизвестный процент → unknown. Заряд ниже minimum → warning.
GPSЕсли GPS не требуется ни policy, ни аппарату → info. Нет валидных данных → unknown. Fix ниже 3D или недостаточно спутников/слишком большой HDOP → warning.
HomeНет live → unknown. Проверка необязательна → info. Требуется Home, но координата невалидна → warning. Валидная (0,0) допустима.
SensorsНе reported ни одного enabled/present датчика → unknown. Среди включённых датчиков есть unhealthy → warning.
RCНе обязателен → info. При обязательной проверке receiver не reported → unknown. Enabled + healthy → OK, иначе warning.
MissionПередача идёт → unknown. Есть несинхронизированные изменения dirty → warning. Пустая миссия → warning, если required, иначе info. Непустая синхронизированная → OK при live.
Autopilot readinessПрошивка не предоставляет результат → unknown. Не готов → warning. Готов → OK при live.
Summary / attentionInfo не увеличивает число OK. Фильтр attention показывает warning и unknown в исходном порядке.

3. Не менять строгие границы порогов

Примеры при minimumBatteryPercent = 40, maximumPacketLoss = 10
39% заряда  → ниже минимума → warning
40% заряда  → не ниже минимума
41% заряда  → не ниже минимума

10% потерь   → не выше максимума
10.1% потерь → выше максимума → warning

// Сравнения остаются такими:
percent < minimumBatteryPercent
loss > maximumPacketLoss

Равенство порогу само по себе не создаёт warning. Но другая причина, например chargeState=fault, всё равно может дать warning при 90% заряда.

Две особенности, которые легко неверно истолковать

  • GPS satellites=255 означает неизвестное число, но существующий C++ уже преобразует его в 0. Поэтому исходная логика иногда выдаёт warning о недостатке спутников вместо unknown. Сохраните поведение при миграции.
  • mavlinkLossPercent — сглаженный показатель на основе накопленных потерь. Это не RSSI и не процент потерь только за последнюю секунду. Не меняйте его смысл в подписях.

Как проверить результат

  1. Проверены значения ниже, ровно на и выше каждого порога.
  2. Healthy первая батарея не скрывает fault второй.
  3. При link loss старые значения не дают ложного OK.
  4. Unknown не превращается в нулевое «хорошее» значение, info не считается OK.

3. Сделать отчёт именно снимком

При Capture зафиксируйте время new Date().toISOString(), автоматические статусы, все ручные проверки и note.trim(). Сохраните получившуюся строку в report. Новые пакеты телеметрии после этого не переписывают текст — его можно спокойно выделить и скопировать.

Следующий Capture заменяет снимок новым. Capture допустим offline: он покажет соответствующие неизвестные результаты. Заметка ограничена 4 000 символами; Reset очищает её вместе с отчётом.

Эта функция не отправляет MAVLink-команд, не меняет параметры аппарата и не сохраняет отчёт на диск автоматически.

Как проверить результат

  1. Отметьте пункт и введите заметку; закройте и откройте popup — данные на месте.
  2. Смените аппарат, выключите monitoring или выполните disarm — сессия очищается.
  3. Отдельно проверьте, что arm и редактирование порогов её не очищают.
  4. Capture остаётся неизменным после новой телеметрии; следующий Capture обновляет текст и ISO-время.
  5. Reset Cancel сохраняет состояние, Reset Confirm очищает только сессию.

«Gate» означает дополнительное условие: панель видна, только если выполняются прежние условия и пользователь включил новый флаг. Прежние проверки камеры, full-screen и прочие условия сохраняются.

Зачем скобки: исходные возможности камеры объединены оператором || («или»). Новый флаг должен применяться ко всему выражению. Без скобок && («и») может ограничить только последний вариант, и камера останется видимой при выключенном флаге.

4. GPS - код переносить не требуется

Нужное пользовательское исправление — отметить, что GPS-телеметрия поступила, — уже реализовано в целевой версии. Поэтому здесь задача состоит в проверке поведения, а не в копировании старых файлов.

Что означает telemetryAvailable

До поступления данных GPS FactGroup не должен считаться источником полученной телеметрии. После обработки соответствующего сообщения вызывается _setTelemetryAvailable(true). Snapshot читает этот признак, чтобы отличать отсутствие данных от валидного результата.

Сообщение MAVLinkЧто проверить
GPS_RAW_INTОсновной GPS: после декодирования доступны данные и выставлен признак
GPS2_RAWВторой GPS: аналогичная обработка
HIGH_LATENCYGPS-данные из сообщения для высоколатентной связи
HIGH_LATENCY2Другая версия высоколатентного сообщения; сохранить её масштабы значений

Где смотреть

Проверьте соответствующие обработчики в src/Vehicle/FactGroups/VehicleGPSFactGroup.cc и VehicleGPS2FactGroup.cc. Подтвердите также нормализацию координат, единиц измерения и специальных значений «неизвестно».

Sentinel — специальное число, обозначающее отсутствие значения. Например, спутники=255 не означают 255 реально видимых спутников; исходная нормализация превращает это в 0. Для DOP существуют свои sentinels и масштабы.

Почему опасно заменить эти файлы старыми

  • yaw — дополнительные данные направления, которых старая версия могла не учитывать.
  • GNSS_INTEGRITY — сведения о состоянии/целостности GNSS.
  • Aggregate behavior — совместная обработка состояния нескольких GPS.

Замена целого файла старой реализацией может удалить эти новые возможности. Дедупликация GPS1/GPS2 — уборка повторяющегося кода — необязательна для переноса функций и выполняется отдельно.

Как проверить результат

  1. До первого сообщения availability не утверждает, что данные уже получены.
  2. После каждого из четырёх типов сообщения соответствующая availability становится true.
  3. Координаты, DOP и sentinels отображаются корректно.
  4. Подготовка получает обновлённый GPS-статус; yaw, integrity и aggregate остаются в целевой реализации.

2. Сопоставлять по смысловому ключу

Существующие TS целиком не заменяйте. Переносите применимые записи, сохраняйте новые целевые сообщения и актуальные locations. Устаревшие ключи без используемого сообщения не восстанавливайте.

4. Не повредить подстановки и перечисления

Placeholder — место под значение, которое приложение подставит позже. В Battery %1 номер батареи появится вместо %1. В переводе должен остаться тот же маркер:

Правильно и неправильно
Источник: Battery %1
Правильно: Батарея %1
Неправильно: Батарея 1
Неправильно: Батарея $1
Неправильно: Батарея %s
Неправильно: Батарея % 1
  • Не теряйте %2 и другие маркеры; сохраняйте число их употреблений. Порядок фразы может меняться, сами имена подстановок — нет.
  • Проверяйте %n для форм множественного числа, переносы строк и HTML-теги в тех сообщениях, где они используются.
  • В JSON enumStrings подписи соответствуют enumValues по порядку. Нельзя переставить «Включено/Выключено» местами или добавить лишнюю подпись: изменится смысл выбора.

5. Разобрать полный реестр и собрать QM

Краткий GUIDE не перечисляет все 4 128 различий. Для массовой работы используйте TRANSLATION_MIGRATION.json или .md из анализа. В этой HTML-инструкции реестр не встроен. Если его нет, сначала сформируйте сравнение TS по ключам и отдельно разберите неоднозначные совпадения.

После переноса соберите QM штатным процессом проекта / lrelease. Один только исправленный TS не гарантирует, что приложение действительно загрузило новый перевод.

Как проверить результат

  1. Новые строки подготовки попали в source/JSON-каталоги.
  2. Ключи сопоставлены по context/source/comment; неоднозначные случаи просмотрены.
  3. Подстановки и HTML валидны, enumStrings соответствуют enumValues.
  4. Собраны QM; RU интерфейс и живые сообщения отображаются правильно.

6. Docker / Android / GStreamer

Здесь переносится способ сборки и выдачи приложения: удобные команды, версии Android и выбор внешнего видео-SDK. Основой остаются Docker/CMake-файлы целевой версии.

ТерминЧто означает
Docker imageПодготовленная среда с компилятором, Qt и зависимостями
WrapperНебольшой shell-скрипт, который удобно вызывает целевой механизм сборки
CMake / NinjaНастройка сборки и выполнение компиляции в целевой версии
APK / AppImageГотовые пакеты Android / Linux, получаемые после сборки
GStreamer SDKБиблиотеки, заголовки и инструменты для видео

Используйте deploy/docker/Dockerfile, run-docker.sh, _docker-exec.sh, entrypoint.sh и версии из .github/build-config.json. Старые Qt5/qmake Dockerfile и .dockerignore целиком не переносите: они предназначены для другого процесса сборки.

Следующие подразделы объясняют три независимых результата: удобные команды Docker, правильный versionCode APK и выбор внешнего GStreamer.

Docker wrappers

Wrapper — привычная команда поверх нового механизма. Снаружи можно сохранить старое имя, внутри нужно вызывать целевую сборку.

При необходимости создать совместимые команды
create_ubuntu_docker.sh
create_android_docker.sh
build_ubuntu_docker.sh
build_android_docker.sh

1. Строить нужную среду и разделить каталоги

В целевом Dockerfile есть targets linux и android. Это разные среды сборки. Настройки CMake кэшируются, поэтому один каталог build для обоих использовать нельзя:

Пример создания образов из корня проекта — shell Linux/WSL
docker build -f deploy/docker/Dockerfile --target linux -t qgc-linux .
docker build -f deploy/docker/Dockerfile --target android -t qgc-android .

# Для результатов сборок используйте разные host directories:
# build-linux/
# build-android/

Это команды создания images. Запуск самой сборки адаптируйте к целевым run-docker/_docker-exec/entrypoint; не возвращайте qmake из старого wrapper.

2. Сохранить удобные параметры пользователя

Переменные окружения со старыми именами images и UID/GID можно сохранить как aliases. Wrapper читает их и передаёт в новый механизм. UID/GID — идентификаторы пользователя/группы в Linux: runtime user mapping позволяет создавать файлы, доступные пользователю хоста, без запекания личных ID в image.

3. Упаковывать и переименовывать после успешной сборки

Используйте целевой qgc-package и фактический путь полученного файла. Старый путь build/staging или имя APK могут больше не соответствовать результату. Сначала убедитесь, что сборка успешна и найден правильный артефакт, затем добавляйте суффикс версии.

git describe получает имя версии из Git. Если исходники выданы архивом без .git, wrapper должен принимать явную версию или завершаться с понятным сообщением, а не выпускать пакет с пустым/случайным именем.

4. Сохранить Android caches и тот же сертификат

  • .gradle хранит данные Gradle и ускоряет повторные сборки.
  • .android может содержать пользовательские Android-данные и debug keystore.
  • Signing keystore хранит ключ подписи. Новый APK для обновления уже установленного должен иметь совместимую подпись; смена ключа помешает обычному обновлению.
Проверка реально полученного APK
apksigner verify --print-certs path/to/built.apk
# Подставьте фактический путь APK вашей сборки.
# Сравните сертификат с предыдущим установленным APK.

Целевая сборка может выдать unsigned APK. В таком случае требуется предусмотренный этап подписи; успешная компиляция сама по себе не означает готовность к обновлению на устройстве.

5. Не исключить нужные файлы из Docker context

Docker context — набор файлов, которые доступны командам COPY при создании image. Старые правила * и !deploy/docker/* скрывают почти всё. Новый Dockerfile использует также .github/build-config.json, tools/* и deploy/docker/lib; эти пути должны остаться доступны.

Старые user_config.pri и install-qt-linux.sh не возвращайте: используйте целевую систему настройки и установки зависимостей.

Как проверить результат

  1. Linux и Android используют разные build directories.
  2. Старые env aliases работают; результаты доступны host user.
  3. Повторный запуск сохраняет Gradle cache и нужный keystore.
  4. Пакет найден по реальному output path; без .git версия обрабатывается явно.
  5. apksigner подтверждает подпись; новый APK устанавливается обновлением.

Android versionCode

versionCode — числовая версия Android-приложения. Она отличается от красивой строки названия версии: Android использует число для определения, можно ли установить APK как обновление.

1. Добавить необязательное внешнее значение

В старой версии override находился в QGCCommon.pri. В целевой версии добавьте поддержку QGC_ANDROID_VERSION_CODE_OVERRIDE в cmake/platform/Android.cmake. Назначьте override после расчёта обычного ANDROID_VERSION_CODE, но до установки свойства QT_ANDROID_VERSION_CODE.

Порядок действий — псевдокод, не готовый CMake-фрагмент
1. Вычислить штатный ANDROID_VERSION_CODE целевой версии.
2. Выбрать override: CMake cache, иначе environment.
3. Если override отсутствует — оставить штатное значение.
4. Если задан — проверить формат и диапазон.
5. Назначить валидный override в ANDROID_VERSION_CODE.
6. Установить QT_ANDROID_VERSION_CODE для target.

2. Проверять ввод и приоритет источников

  • Допустимо положительное десятичное целое в диапазоне 1…2100000000.
  • Отрицательные, дробные, нечисловые и слишком большие значения должны завершать configure с ошибкой.
  • Cache > env: значение, явно переданное через -D, имеет приоритет над одноимённой переменной окружения.
  • Отсутствие override — нормальный случай, тогда работает штатная формула.
Пример аргумента configure после реализации поддержки override
-DQGC_ANDROID_VERSION_CODE_OVERRIDE=1262901200

Это аргумент к вашей реальной команде CMake/qt-cmake, а не самостоятельная команда shell. Пример числа не гарантирует, что оно больше уже установленного APK: сравните с фактической предыдущей версией.

3. Передать одно число во все ABI

ABI — вариант сборки под архитектуру процессора, например arm64-v8a. Если Qt запускает несколько sub-configures для разных ABI, добавьте override в QT_ANDROID_MULTI_ABI_FORWARD_VARS. Все части одной сборки должны получить одно значение, вычисленное заранее.

4. Обеспечить рост версии

Старый wrapper использовал UTC-дату:

Прежний способ генерации — shell
date -u '+1%y%j%H%M'

Это префикс 1, год, день года, часы и минуты. Две сборки в одну минуту могут получить одинаковое число, а перевод часов назад может уменьшить его. Для CI лучше один монотонно растущий счётчик. Любая схема должна давать число больше versionCode предыдущего устанавливаемого APK.

Как проверить результат

  1. Без override получается штатное значение цели.
  2. С явно заданным -D получается нужный versionCode в итоговом APK.
  3. Некорректные значения отвергаются на configure.
  4. Все ABI получают одно число; APK обновляет предыдущую установку без ошибки downgrade.

Внешний GStreamer

GStreamer обеспечивает видеопотоки. Если SDK установлен отдельно от проекта, сборке нужно указать правильную папку SDK. В целевой версии для этого уже существует GStreamer_ROOT_DIR.

1. Различить universal root и SDK конкретного ABI

Условный пример структуры внешнего Android SDK
/opt/gstreamer-sdk/        # universal root — несколько архитектур
    armv7/
    arm64/                 # SDK root для arm64
        include/
        lib/
            pkgconfig/
    x86_64/

Старый GSTREAMER_HOME мог указывать на верхнюю папку со всеми архитектурами. Целевому configure нужен root выбранного ABI, например arm64, а не случайно armv7 или весь universal root.

2. При необходимости поддержать старое имя переменной

  1. В wrapper прочитайте GSTREAMER_HOME, если пользователь его задал.
  2. Выберите подкаталог по фактическому ABI сборки.
  3. Проверьте наличие include, lib и pkgconfig, а также версию SDK.
  4. Передайте получившийся путь в configure как GStreamer_ROOT_DIR.
  5. Если внешнее значение не задано, не вмешивайтесь: оставьте штатный resolver/download целевой версии.
Аргумент к вашей команде configure — путь только для примера
-DGStreamer_ROOT_DIR=/opt/gstreamer-sdk/arm64

3. Проверить совместимость версии

Старый GStreamer 1.18.6 ниже указанного в руководстве минимума целевой версии 1.20. Для зафиксированной при анализе цели использовался SDK 1.28.4. Версию вашей рабочей копии берите из .github/build-config.json; SDK должен совпадать с требуемой архитектурой и целевыми библиотеками.

Проверки include/lib/pkgconfig подтверждают структуру, но сами по себе не доказывают совместимость. Неверный ABI или версия должны быть выявлены при настройке/сборке. Изменять код видеоплеера только ради alias переменной не требуется.

Как проверить результат

  1. С внешним SDK configure действительно выбирает указанный путь.
  2. Без GSTREAMER_HOME работает штатный способ поиска/загрузки.
  3. Неподходящий SDK не используется молча.
  4. На нужной платформе проверены UDP/RTSP, запись и её завершение.

Итоговая проверка после переноса

Эти проверки объединяют разделы руководства. Выполняйте их на рабочей копии проекта и тестовом профиле. Приведённые примеры кода объясняют изменения, но не означают, что они уже скомпилированы и испытаны в вашем QGC.

  1. Сборка проходит, новые QML/JS и metadata найдены в ресурсах.
  2. Подготовка открывается offline и содержит все пять страниц.
  3. Настройки сохраняются после перезапуска; невалидный ввод отклоняется.
  4. Переключение двух аппаратов и появление второй батареи обновляют правильные данные.
  5. Link loss и disarm сбрасывают сессию; закрытие окна её сохраняет.
  6. Пороговые значения, неизвестная телеметрия, пустая/dirty/loading миссия оценены корректно.
  7. Снимок отчёта не меняется сам, заметка ограничена 4 000 символами.
  8. Четыре visibility-флага не ломают раскладку и не прекращают запись видео.
  9. Порядок меню изменён; новый review параметров сохранён.
  10. GPS upstream, переводы и упаковка проверены; Android APK обновляет предыдущую установку.
